# 04 · 排错手册

**[简体中文](04-排错手册.md)** · **[English](04-troubleshooting.en.md)**

## 快速自查

```bash
./bin/jyfree --process     # 找到 Student 了吗?
id -u; ps -o uid= -p $(pgrep Student | head -1)   # UID 一致吗?
./scripts/build.sh --check # 编译环境对吗?
cat /tmp/jyfree-payload.log   # payload 说什么了?
./bin/jyfree -d 5           # 控制器详细日志
```

---

## 1. 找不到 Student

```
[WARN] 未找到 Student 进程
```

### 原因与处理

**① 极域还没启动**

看门狗会自动等待。启动极域后应该自动注入，或手动：

```bash
> inject
```

**② 进程名不对**

```bash
./bin/jyfree --process
pgrep -a -f mythware
pgrep -a Student
```

Linux 版进程名是 `Student`（不是 Windows 的 `StudentMain.exe`）。

**③ 你看到的进程不是主程序**

极域有三个进程：

| 进程 | UID | 说明 |
|---|---|---|
| `Student` | 用户 | **注入目标** |
| `StudentAgent` | 用户 | 看门狗，托盘 |
| `StudentService` | **root** | 策略执行（不可注入） |

---

## 2. `PTRACE_ATTACH 被拒绝`

```
[ERROR] PTRACE_ATTACH 被拒绝 (pid=12345): 需要同 UID 运行
```

### 原因

`ptrace` 要求 tracer 与 target 同 UID。

### 检查

```bash
# 本工具 UID
id -u

# Student UID
ps -o uid=,user= -p $(pgrep Student | head -1)
```

### 处理

用**极域所在的用户**运行本工具：

```bash
# 切换到该用户
su - <极域用户名>

# 或用该用户身份执行
sudo -u <极域用户名> ./bin/jyfree
```

> 极域是开机自启的桌面程序，通常就是当前登录用户。
> **不要用 root 跑** —— root 能 ptrace，但注入后 payload 在 `Student` 里以
> `Student` 身份运行，共享内存权限和计数器语义会不一致。

**不需要 Yama ptrace_scope 放行** —— 实测目标机没有 Yama。

## 3. `payload 未在超时内就绪`

```
[ERROR] payload 未在超时内就绪 (检查 /tmp/jyfree-payload.log)
```

### 3.1 架构不匹配（最常见）

payload 的内联钩子地址（`0x441ed4` 等）是 **aarch64 专用**。

```bash
file bin/libjyfree.so
# 必须是: ELF 64-bit LSB shared object, ARM aarch64
```

如果不是 aarch64，重新交叉编译：

```bash
./scripts/build.sh --cross
```

### 3.2 payload 找不到

```bash
ls -l bin/libjyfree.so
ls -l $(dirname $(readlink -f $(which jyfree)))/libjyfree.so
```

`payload_path()` 查找顺序：`/proc/self/exe` 同目录 → `/usr/local/lib/` →
`/usr/lib/` → `./`。**jyfree 与 libjyfree.so 必须在同一目录。**

### 3.3 符号地址版本不符

```bash
cat /tmp/jyfree-payload.log | grep "内联钩子"
```

如果日志里有 `写内存失败` 或 `段错误`，多半是版本变了：

```bash
nm /opt/mythware/classroom-management/Student | grep ShowLockScreen
```

与 `include/payload_state.h` 中的 `SYM_ShowLockScreen` 比对，不一致就更新。

### 3.4 共享内存没建起来

```
[ERROR] 创建共享内存失败
```

```bash
ls -ld /dev/shm
mount | grep shm
```

修复：

```bash
sudo mount -t tmpfs -o rw,nosuid,nodev,noatime tmpfs /dev/shm
```

## 4. `目标进程处于 'T' 状态`

```
[WARN] 目标进程处于 'T' 状态, 跳过注入 (需先 SIGCONT)
```

Student 被 `SIGSTOP` 冻结了。逆向分析里也观察到过这个现象，
成因未定论（厂商重启时序 or 人为实验）。

```bash
> thaw
```

或：

```bash
kill -CONT $(pgrep Student | head -1)
```

## 5. 注入成功但 `counters` 全是 0

```
拦截计数:
  锁屏 0
  监视 0
  ...
```

这是**正常**的 —— 计数只在教师**实际操作**时增长。

```bash
# 1. 确认 payload 活着
> status
  payload 心跳:   1757000000000     ← 每秒变化 = 正常
  已装钩子数:     16

# 2. 确认目标库已加载
> modules
  [已加载] libDesk.so.2
  [未加载] libcast-x11.so       ← 教师没开始广播，所以没加载
```

判读：

| 现象 | 结论 |
|---|---|
| 心跳不变 | payload 线程死了 → 看门狗会重注入，或手动 `inject` |
| 钩子数 = 0 | 内联钩子没装上 → 符号地址不符或库未加载 |
| 钩子数 < 16 | 部分库当时没加载（正常，libcast-x11 按需加载） |
| 库已加载但计数 0 | 教师还没操作对应功能 |

## 6. 截屏拦截无效

```
counters 的「截屏」一直是 0
```

### 两条路径

```
路径 A: 监视/截屏  → libDesk.so.2 → XGetImage      ← 本工具覆盖
路径 B: 教师广播  → RDP 流 → libcast-x11.so         ← 不同路径
```

路径 B 的数据**不经过 `XGetImage`**，所以截屏计数不会涨。

### 验证走的是哪条

```bash
> modules
  [已加载] libDesk.so.2         ← 监视在用
  [已加载] libcast-x11.so       ← 广播在用
```

教师开始广播后 `libcast-x11.so` 会被 dlopen，payload 会在 1 秒内自动补钩
（日志里有 `检测到 libcast-x11.so 已加载, 扫描其 GOT`）。

### 已知限制

`libcast-x11` 走的是 freerdp 的 RDP 通道，帧数据在专用缓冲区里，
`XGetImage` 钩子可能覆盖不到。**这一条尚未验证**，需要课堂实测。

## 7. 输入拦截无效

### 7.1 Qt 的窗口不受影响（正常）

Qt 走 **xcb** 不经 Xlib → 封 Xlib 不影响 Qt 窗口系统。
这是**预期行为**。

### 7.2 教师键鼠仍然有效

先确认 freerdp 输入回调钩子装上了：

```bash
cat /tmp/jyfree-payload.log | grep "libcastng"
```

如果显示 `libcastng 未加载, 跳过输入回调钩子`，说明**教师还没开始远程控制**
（libcastng 可能在教师连接时才加载）。

`input` 特性位要开着：

```bash
> feat input on
```

### 7.3 XWayland 的影响

会话是 Wayland，但 Student 跑在 XWayland 上。`XGrabKeyboard`/`XTestFake*`
在 XWayland 里**只影响 X 客户端** —— 极域自己的 X11 代码受影响，
但如果教师控制走的是别的通道（如 Qt 内部），可能拦不住。

需要课堂实测 `counters` 的「输入」计数。

## 8. 看门狗反复重新注入

日志里刷：

```
[INFO] 检测到 Student 新实例 (pid=NNNN), 重新注入
```

### 原因

`Student` 在**崩溃循环**：`CastAudioBase` 析构时
`QThread destroyed while running` → abort coredump → `StudentAgent` 重启。

```bash
# 确认崩溃
dmesg | tail -20 | grep -i segfault
coredumpctl list 2>/dev/null | tail
```

### 这是厂商的 bug，不是本工具的问题。

不影响使用 —— 看门狗会自动跟上。可选缓解：

```bash
# 屏蔽 coredump 写入，减少 IO
sudo sysctl -w kernel.core_pattern='|/bin/true'
```

## 9. 编译问题

见 `docs/02-编译指南.md` 第 8 节。最常见：

| 错误 | 处理 |
|---|---|
| `X11/Xlib.h: No such file` | `sudo apt install libx11-dev`，或只编译 `make cli payload` |
| `'shm_open' undeclared` | Makefile 的 `LIBS` 加 `-lrt` |
| 交叉编译找不到 `aarch64-linux-gnu-gcc` | `sudo apt install gcc-aarch64-linux-gnu` |

## 10. 收集完整信息

报告问题时请附上：

```bash
{
  echo "=== 系统 ==="
  uname -a
  cat /etc/os-release | head -3

  echo "=== 架构 ==="
  ./bin/jyfree --help | head -5

  echo "=== 极域进程 ==="
  ./bin/jyfree --process

  echo "=== 已加载库 ==="
  ./bin/jyfree --modules

  echo "=== 注入状态 ==="
  ./bin/jyfree -d 5 -s

  echo "=== payload 日志 ==="
  tail -50 /tmp/jyfree-payload.log

  echo "=== 控制器日志 ==="
  tail -50 ~/.config/jiyu-trainer/jiyu-trainer.log

  echo "=== 符号地址核对 ==="
  nm /opt/mythware/classroom-management/Student 2>/dev/null \
    | grep -E 'ShowLockScreen|StartMonitorPassive|ExecuteRemoteCmd'
} > /tmp/jyfree-report.txt 2>&1

echo "报告已生成: /tmp/jyfree-report.txt"
```

## 11. 紧急还原

如果钩子导致极域行为异常：

```bash
./bin/jyfree
> uninject      # 触发 destructor, 还原所有内联钩子
> quit
```

或者直接杀掉 Student 让 `StudentAgent` 重启一个干净的：

```bash
kill -9 $(pgrep Student | head -1)
```

最彻底：停掉整个极域

```bash
pkill -9 -f Student
pkill -9 -f StudentAgent
# StudentService 是 root, 需要 sudo
sudo pkill -9 StudentService
```
